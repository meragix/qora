## Objective

Mobile connectivity drops all the time: tunnels, elevators, airplane mode. Apps also get killed while offline. This example shows a todo app that stays usable through both:

- the list is shown from the cache, and from storage on a cold start;
- the UI knows when it is offline, instead of spinning forever;
- todos created, toggled or deleted offline appear immediately, **survive an app restart**, and are sent in order when the network returns;
- a write the server refuses is shown to the user, who decides to resend or drop it.

There is no custom sync code: the app registers its writes, and reads the queue to show what is pending.

:::tip
**Try it without touching your Wi-Fi or killing the app.** The antenna button in the app bar switches the device offline, and the fake API fails while offline. The restart button disposes the client and builds a new one from storage, as a real restart would. The sync button opens the queue. Create a todo whose title contains "reject" to see a write the server refuses.
:::

## Features Demonstrated

- **`PersistQoraClient`**: fetched data and queued writes go to a `StorageAdapter`; `hydrate()` restores both
- **Registered mutations**: `todos.create`, `todos.toggle` and `todos.delete` are declared once, with a serializer for their variables, so a write queued by one session can be sent by the next
- **`meta.mutationId`**: sent as an idempotency key, so a write sent twice is applied once
- **Scopes**: every write to one todo shares the scope `todo:<id>`, so a toggle never overtakes the create of its todo
- **`isPermanent`**: a 4xx is not retried; the write is `blocked` and the writes behind it are `held`
- **`MutationQueueBuilder`**: the list overlays the pending writes from `mutationQueue.entries`, and a sync panel lists them with retry and discard
- **`NetworkMode.offlineFirst`**, **`FetchStatus.paused`**, **`NetworkStatusIndicator`** and **`ReconnectStrategy`** for the read side

## Architecture

```text
main.dart
├── InMemoryStorageAdapter().init()   ← the "disk": survives the simulated restart
├── SimulatedNetwork()                ← the device's network, toggled from the UI
├── TodoApi(network)                  ← the server, with idempotency keys
└── OfflineTodoApp                    ← rebuilds the client on restart
    └── startClient(storage, api)
        ├── PersistQoraClient(...)
        ├── registerAllSerializers()  ← query data written to storage
        ├── registerTodoMutations()   ← writes that can be stored and replayed
        └── hydrate()                 ← cached list, then queued writes
```

Startup follows the order a real app needs: register everything, then hydrate.

```dart [lib/main.dart]
Future<PersistQoraClient> startClient(
  StorageAdapter storage,
  TodoApi api,
) async {
  final client = PersistQoraClient(
    storage: storage,
    persistDuration: const Duration(days: 30),
    config: QoraClientConfig(
      defaultOptions: const QoraOptions(
        staleTime: Duration(minutes: 5),
        networkMode: NetworkMode.offlineFirst,
      ),
      // At most 3 concurrent requests on reconnect, 150 ms jitter.
      reconnectStrategy: const ReconnectStrategy(
        maxConcurrent: 3,
        jitter: Duration(milliseconds: 150),
      ),
      debugMode: kDebugMode,
    ),
  );
  registerAllSerializers(client);
  registerTodoMutations(client, api);
  await client.hydrate();
  return client;
}
```

The simulated restart unmounts the `QoraScope`, which disposes the client: like a killed process, it stops sending and keeps what it stored. Only then is the next client built and hydrated, so two clients never send the same queue.

In a real app, replace `InMemoryStorageAdapter` with an adapter backed by real storage (see the [Persistence recipe](../recipes/persistence.md)), and `SimulatedConnectivityManager` with `FlutterConnectivityManager()`, or use `QoraScope.auto`.

## Implementation Details

### Registering the writes

A write that may be sent by another session cannot live in a widget: after a restart, that widget is gone. Each write is registered once, with its mutator, a serializer for its variables, a scope and the errors that are final.

```dart [lib/features/todos/data/todo_mutations.dart]
void registerTodoMutations(QoraClient client, TodoApi api) {
  // Every write to one todo shares its scope: a toggle queued after an
  // offline create waits for it, and is held if the server rejects it.
  String scope(String id) => 'todo:$id';
  bool isPermanent(Object error) =>
      error is ApiException && error.isClientError;

  client
    ..registerMutation<Todo, CreateTodoInput>(
      'todos.create',
      mutator: (input, meta) async {
        // meta.mutationId stays the same across retries and restarts: the
        // server uses it to apply this write once.
        final todo = await api.createTodo(
          input,
          idempotencyKey: meta.mutationId,
        );
        _patchList(
          client,
          (list) => [...list.where((t) => t.id != todo.id), todo],
        );
        return todo;
      },
      variables: QoraSerializer<CreateTodoInput>(
        toJson: (v) => v.toJson(),
        fromJson: (json) =>
            CreateTodoInput.fromJson(json as Map<String, dynamic>),
      ),
      scope: (input) => scope(input.id),
      isPermanent: isPermanent,
      invalidates: [todosKey],
    );
  // todos.toggle and todos.delete follow the same pattern.
}
```

Two choices make the scopes work:

- **The todo's id is generated on the device**, in `CreateTodoInput.newTodo`, and the server creates as an upsert on it. A todo created offline has its final id at once, so a toggle or a delete queued after it targets it, and lands in the same scope. With server-generated ids, the toggle would need an id that does not exist yet.
- **The mutator patches the cached list** with the server's answer. The queue drops a call as soon as it succeeds, and the list shows pending writes from the queue (below): without the patch, a new todo would vanish until the refetch triggered by `invalidates` completes.

### Calling them

Call sites name the key; they pass no mutator.

```dart [lib/features/todos/ui/todo_screen.dart]
QoraMutationBuilder<Todo, CreateTodoInput, void>(
  options: const MutationOptions(
    mutationKey: 'todos.create',
    offlineQueue: true,
  ),
  // Never disabled while a call is pending: offline, each new todo is
  // queued behind the others, and shows in the list at once.
  builder: (context, _, create) => FloatingActionButton.extended(
    onPressed: () async {
      final title = await _askTitle(context);
      if (title != null) await create(CreateTodoInput.newTodo(title));
    },
    icon: const Icon(Icons.add),
    label: const Text('Add Todo'),
  ),
)
```

Every call goes through `client.mutationQueue`, online or not, and is written to storage before `mutate` returns.

### Showing pending writes from the queue

The list is the server's data with the queued writes laid over it. The pending state is read from the queue rather than written into the cache by `onMutate`: the queue is stored and restored, optimistic cache writes are not. So a todo created offline still shows after a restart, until the server confirms it.

```dart [lib/features/todos/ui/todo_screen.dart]
MutationQueueBuilder(
  builder: (context, entries, _) => _TodoList(
    todos: applyQueue(state.dataOrNull ?? const [], entries),
    isRefreshing: fetchStatus == FetchStatus.fetching,
    isOffline: fetchStatus == FetchStatus.paused,
  ),
)
```

`applyQueue` is a pure function: a queued create adds its todo, a toggle changes it, a delete on its way hides it. Each todo gets a sync state, from its writes' statuses:

```dart [lib/features/todos/data/todo_view.dart]
for (final entry in queue) {
  switch (entry.variables) {
    case CreateTodoInput(:final id, :final title):
      todos[id] ??= Todo(id: id, title: title, completed: false);
      mark(id, entry.status);
    case ToggleTodoInput(:final id, :final completed):
      final todo = todos[id];
      if (todo != null) todos[id] = todo.copyWith(completed: completed);
      mark(id, entry.status);
    case DeleteTodoInput(:final id):
      mark(id, entry.status);
      // A delete on its way hides the todo; a refused one leaves it shown,
      // flagged, so the user can see what did not go through.
      if (sync[id] == SyncState.pending) todos.remove(id);
  }
}
```

### The sync panel

The app bar shows how many writes are waiting, in red when one needs the user. The panel lists `entries` live, and offers a decision on a `blocked` or `failed` write:

```dart [lib/features/sync/sync_panel.dart]
trailing: _needsDecision(entry)
    ? Row(
        mainAxisSize: MainAxisSize.min,
        children: [
          // Same payload, same mutationId: the server still
          // deduplicates it.
          TextButton(
            onPressed: () => queue.retry(entry.mutationId),
            child: const Text('Retry'),
          ),
          // The writes it held become blocked in turn.
          TextButton(
            onPressed: () => queue.discard(entry.mutationId),
            child: const Text('Discard'),
          ),
        ],
      )
    : null,
```

### Scenarios to try

```text
Offline, then restart
  1. Go offline, create "Buy milk"   → stored, shown with a pending icon
  2. Restart                         → hydrate() restores it: still shown, still pending
  3. Go online                       → sent under the same mutationId, confirmed

Killed in flight
  1. Online, create "Call mom", restart at once
  2. The server applied the first request; the new session sends it again
  3. Same mutationId: the server returns the first result, one todo only

Refused
  1. Offline, create "Please reject me", then tick it
  2. Go online                       → create refused (422): blocked; the toggle is held
  3. Sync panel → Discard            → the toggle becomes blocked: discard it too
```

The example's widget tests run these three scenarios.

### Offline with nothing in the cache

When the device is offline and nothing is cached, the fetch pauses instead of running: the state is `Loading` with no previous data, and `fetchStatus` is `FetchStatus.paused`. A spinner would spin until the network returns, so this case gets its own screen:

```dart [lib/features/todos/ui/todo_screen.dart]
if (state.dataOrNull == null && fetchStatus == FetchStatus.paused) {
  return const _OfflineEmptyState();
}
```

## Limits to Know

- **This demo uses `InMemoryStorageAdapter`**: storage survives the simulated restart, not a real one. With a disk-backed adapter, the same code restores the list and the queue on a cold start.
- **Delivery is at-least-once.** The fake server deduplicates on the idempotency key; a real server must do the same, or create with client-generated ids as upserts.
- **Callbacks at the call site do not run after a restart.** The registration's `invalidates` does, which is why the list reconciles from the server, and why the mutator patches the cache.
