Most libraries treat "offline" as one more error. Qora treats it as a state: reads **pause** instead of failing, writes can be **queued**, and both resume on their own when the network returns. This page describes the model; the [Network-Aware recipe](../recipes/network-aware.md) covers configuration in detail.

## How Qora knows the device is offline

The client listens to a `ConnectivityManager`. `QoraScope.auto` attaches `FlutterConnectivityManager`, built on `connectivity_plus`, so a standard Flutter setup needs nothing more.

Two consequences worth knowing:

- **Without a connectivity manager, the client assumes it is online.** Nothing pauses, and nothing replays on reconnect. A pure Dart app can attach its own with `client.attachConnectivityManager(...)`.
- **Connectivity means a network interface, not a reachable server.** On a captive portal or with the API down, the device counts as online: requests run, are retried, and end in `Failure`.

## Two axes: what you have, and what is happening

A query has a state and a fetch status, and offline handling lives in the second one:

- `QoraState` is **what you have**: `Initial`, `Loading`, `Success`, `Failure`, each carrying data when there is some.
- `FetchStatus` is **what the engine is doing**: `fetching`, `paused` (waiting for the network) or `idle`.

`QoraBuilder` passes both to your builder. The usual offline combinations:

| State | `fetchStatus` | Meaning |
| ----- | ------------- | ------- |
| `Loading`, `previousData` set | `paused` | Offline, cached data available, refetch waiting |
| `Loading`, no `previousData` | `paused` | Offline and nothing cached: show an offline screen, not a spinner |
| `Success` | `paused` | Offline in `offlineFirst` mode: cached data served, refetch waiting |
| `Success` | `idle` | Fresh data, nothing to do |

A fetch started while offline does not throw inside widgets. Called imperatively, `fetchQuery` returns the cached data if there is some, and otherwise throws `QoraOfflineException`.

## Reads: `NetworkMode`

`networkMode` decides what a query does when it must fetch while offline. Set it per query in `QoraOptions`, or for every query in `defaultOptions`.

| Mode | While offline | On reconnect |
| ---- | ------------- | ------------ |
| `online` (default) | The fetch is not sent. State becomes `Loading(previousData: cached)`, status `paused` | The fetch runs |
| `offlineFirst` | With cached data: state stays `Success`, status `paused`. Without: same as `online` | The fetch runs |
| `always` | The fetch is sent anyway, and is retried and fails like any error | Nothing special |

Use `always` for fetchers that do not need the network, such as a local database. Use `offlineFirst` when a screen should never flip to a loading state just because the device went offline.

## Writes: the offline mutation queue

A mutation does not pause. Without opt-in, a mutation called while offline sends its request and fails. With `offlineQueue: true` in its `MutationOptions`, it is queued instead:

```text
mutate(variables) while offline
  1. onMutate runs now           → optimistic cache updates work offline
  2. the call is added to the queue
  3. state: MutationSuccess(isOptimistic: true) if optimisticResponse is set,
            MutationPending otherwise

reconnect
  4. the call is sent, once, in the order it was queued
     success → onSuccess, invalidates, onSettled
     failure → onError(error, variables, context from step 1), onSettled
```

Three properties matter in practice:

- **The queue belongs to the client, not to the widget.** A queued write is sent even if the screen that made it was closed.
- **A failed replay is not retried.** `onError` runs with the snapshot from `onMutate`, so the rollback you wrote for the online case also covers this one. Tell the user there.
- **Order is preserved, dependencies are not checked.** If a queued "create" is rejected, a queued "update" of the same item is still sent, and fails in turn. The [queue of registered mutations](#the-queue-of-registered-mutations) handles both retries and dependencies.

`optimisticResponse` only sets the mutation's own state, for example to show a "queued" badge. Changes to cached query data belong in `onMutate`.

:::note
`QoraMutationBuilder` and `useMutation` both use the queue (`useMutation` since `qora_hooks` 1.3.1). A raw `MutationController` needs `isOnline` and `offlineQueue` passed explicitly.
:::

## The queue of registered mutations

A [registered mutation](./mutations.md#registered-mutations) called with `offlineQueue: true` goes through a second queue, `client.mutationQueue`, built for writes that must eventually reach the server. It differs from the queue above in three ways:

- **Every call goes through it, online or not.** A call made online is queued and sent right away. That way an update made online cannot overtake a create still waiting from offline. A call with `networkMode: NetworkMode.always` skips the queue.
- **Transient failures are retried.** A timeout or a 503 does not drop the write.
- **Dependent writes are held.** When a write is rejected, the writes that depend on it are not sent.

```dart [main.dart]
final client = QoraClient()
  ..registerMutation<Todo, TodoInput>(
    'todos.save',
    mutator: (input, meta) => api.saveTodo(
      input,
      idempotencyKey: meta.mutationId,
    ),
    variables: todoInputSerializer,
    scope: (input) => 'todo:${input.id}',
    isPermanent: (error) => error is ApiException && error.statusCode < 500,
  );
```

```dart [todo_editor.dart]
MutationOptions<Todo, TodoInput, void>(
  mutationKey: 'todos.save',
  offlineQueue: true,
)
```

### Scopes

Calls with the same `scope` form a lane: they are sent one at a time, in the order they were made. Calls without a scope share one global lane. Lanes do not wait for each other, and send concurrently up to `ReconnectStrategy.maxConcurrent` requests.

A scope says "these writes depend on each other". Pick the narrowest one that covers the dependencies, usually the record's ID, or the parent's ID for children: a task created inside a project created offline must use the project's scope, or it can be sent before the project exists. A wider scope holds more writes than needed when something fails.

### Failures

Qora does not see HTTP status codes, so the app classifies errors with `isPermanent`, on the registration or for every key in `MutationQueueConfig`:

- **Transient** (the default, when no predicate says otherwise): the call stays at the head of its lane and is retried with exponential backoff while the device is online. The delays double from 1 s up to 30 s, and each one is drawn between half and all of that value: 0.5 to 1 s, then 1 to 2 s, 2 to 4 s, 4 to 8 s. Losing the network during a request does not count as an attempt; the call is sent again on reconnect. After `maxAttempts` (5) attempts, the call is treated as permanent.
- **Permanent**: the call is not retried. In a scope it becomes `blocked`, and the calls behind it in that scope are `held`: an update sent after a rejected create could otherwise create the record with data that never passed validation. Without a scope it becomes `failed`, and the global lane continues.

Without any `isPermanent`, a validation error is retried for 7.5 to 15 seconds of backoff, plus the time of the five requests, before it becomes `blocked` or `failed`. Define it to stop sooner.

### Reading the queue

`client.mutationQueue.entries` lists the queued calls, in order. Each `QueuedMutation` carries its `key`, `scope`, `variables`, `mutationId`, `attempts`, `lastError` and `status`:

| Status | Meaning |
| ------ | ------- |
| `queued` | Waiting for its turn, the network, or its next retry |
| `sending` | Request in flight |
| `blocked` | Waits for a decision: it failed for good at the head of its scope, or a call before it in the scope was discarded |
| `held` | Behind a `blocked` call in the same scope; not sent |
| `failed` | Failed for good without a scope; out of the replay order |

A call leaves the queue when it succeeds or when the app discards it. It appears once it is in the queue for good: after its `onMutate` ran and, with `PersistQoraClient`, once it is stored.

`entriesStream` emits the new entries each time they change: a call queued, sent, retried, failed, discarded or done. Changes made in one synchronous run are reported once. In Flutter, [`MutationQueueBuilder`](../flutter-integration/network-status.md#mutationqueuebuilder) reads `entries`, listens, and rebuilds on every change:

```dart [sync_badge.dart]
MutationQueueBuilder(
  builder: (context, entries, child) => entries.isEmpty
      ? const SizedBox.shrink()
      : Text('${entries.length} change(s) to sync'),
)
```

Without the widget, read `entries` first, then listen to `entriesStream`.

With `qora_hooks`, [`useMutationQueue()`](../flutter-integration/hooks.md#usemutationqueue) returns the same list and rebuilds on every change.

A call with no caller left, because it was restored after a restart or retried after its call site settled, reports to `client.mutationEvents` under the id `queue:<mutationId>`: `pending` when it is first sent, then `success` or `error`. Its `metadata` carries `mutationKey` and `mutationId`.

### Deciding on a blocked or failed call

```dart [sync_screen.dart]
final queue = client.mutationQueue;

// Resend as-is, under the same mutationId.
queue.retry(entry.mutationId);

// Replace it with corrected variables, under a new mutationId.
queue.retry(entry.mutationId, variables: fixedInput);

// Drop it. The calls it held become blocked in turn.
queue.discard(entry.mutationId);

// Drop the whole chain.
queue.discardScope('todo:42');
```

- **`retry(id)`** resends the same payload under the same `mutationId`, so server-side deduplication still applies. Use it when a call ran out of attempts on transient errors: the server may have applied it already.
- **`retry(id, variables: ...)`** replaces the call in place, under a new `mutationId`. To change a record whose write is blocked, retry that write with new variables instead of calling `mutate` again: a new call would be held behind the blocked one, and the queue would hold two versions of the record.
- **`discard(id)`** removes the call. The calls behind it in its scope may target a record that will never exist, so they become `blocked`, and the user decides for each. A call discarded while its request is in flight leaves `entries` at once and is not retried; if that request succeeds anyway, the registration's invalidations run, and the calls behind it stay `blocked`.
- **`clear()`** empties the queue. Call it on logout: a queued write belongs to the user who made it. Clear the queue before the cache (`client.mutationQueue.clear()`, then `client.clear()`): the `onError` rollbacks it runs write to the cache. `PersistQoraClient.clear()` does both, in that order.

`discard`, `discardScope` and `clear` settle each removed call made in this session as a failure: its `onError` receives a `MutationDiscardedException` with the `onMutate` context, so the rollback written for a rejected write also undoes an abandoned one.

### What the call site sees

The call site's callbacks run for calls made in this session, even after its widget is unmounted, so an `onError` rollback still reaches the cache. They run once per call: when it succeeds, or when it fails for good. A later `retry` of that call runs only the registration's invalidations, since the `onMutate` snapshot is stale by then, and the controller that made the call stays in `MutationFailure` even if the retry succeeds. An error thrown by these callbacks goes to the current `Zone` instead of to the caller of `mutate`.

`mutate` resolves when the call succeeds, fails for good, or starts waiting (offline, behind a held scope, behind or at a lane head waiting for a retry). In the last case it resolves with `null`, or with the `optimisticResponse` result when the device was offline at call time, and the mutation state stays `MutationPending` (or that optimistic `MutationSuccess`) until the call settles.

The queue's policy replaces the call site's `retryCount`, `retryDelay` and `retryCondition` for these calls.

Disposing the client completes every pending `mutate` with `null` and runs no callbacks: the app is shutting down, and the cache goes with it. With `PersistQoraClient`, the stored calls are kept and sent at the next start.

With `PersistQoraClient`, the queue survives a restart: see [Persisting the queue](#persisting-the-queue).

## Reconnect

When the connectivity manager reports the network is back, the client:

1. **Replays paused queries** in batches. `ReconnectStrategy` sets the batch size and a random delay between batches (default: 5 at a time, up to 100 ms), so a hundred paused queries do not hit the server at once.
2. **Then replays the mutation queue** above, after the reads, one mutation at a time.

The queue of registered mutations does not wait for the reads: it resumes as soon as the network is back, lane by lane, and calls waiting for a retry delay are sent right away.

Independently, `QoraScope.auto` also refetches stale on-screen queries when the app returns to the foreground.

## Across restarts

| What | Survives a restart? |
| ---- | ------------------- |
| Cached query data | Yes, with `PersistQoraClient` and a `StorageAdapter`. See [Persistence](../recipes/persistence.md) |
| Registered mutations in the queue | Yes, with `PersistQoraClient`, in the same `StorageAdapter` |
| Calls without `mutationKey` | No: `OfflineMutationQueue` lives in memory |

### Persisting the queue

With `PersistQoraClient`, each registered call is written to storage before it counts as queued: `mutate` resolves, and the `optimisticResponse` shows, only once the write has completed. If the write fails, the call fails with that error and `onError` runs. An app must never tell its user "saved" for a write that only exists in memory. The calls behind it in its scope become `blocked`.

Each call is its own entry, under a key that starts with `qora:mutation:`, so it never collides with query keys or with app keys in a shared Hive box or `SharedPreferences`. Its variables go through the registration's `variables` serializer once, and the mutator receives them decoded from what was stored, so every attempt sends the same payload, in this session or after a restart. Changing the variables object after calling `mutate` changes nothing. The entry is updated after each failed attempt, and deleted after a success or a discard. A `retry` is stored before it is sent; if that write fails, the call waits for a decision again, with the storage error as `lastError`.

Register every mutation before `hydrate()`:

```dart [main.dart]
final client = PersistQoraClient(storage: storage)
  ..registerMutation<Todo, NewTodo>(
    'todos.create',
    mutator: (input, meta) =>
        api.createTodo(input, idempotencyKey: meta.mutationId),
    variables: QoraSerializer<NewTodo>(
      toJson: (v) => v.toJson(),
      fromJson: (json) => NewTodo.fromJson(json as Map<String, dynamic>),
    ),
    invalidates: [['todos']],
  );

await storage.init();
await client.hydrate(); // restores the cache, then the queue
```

`hydrate()` restores the queue ahead of the calls made before it that are not sent yet, with each call's `mutationId`, attempts and status, and starts sending. A call made before `hydrate()` may already be in flight, so hydrate before the app can mutate. A stored call whose key is not registered, or whose variables `fromJson` rejects, stays in storage but is not restored; nor are the later stored calls of its scope, so they are never sent before it. Calls made in this session in that scope are not held: register every key before `hydrate()`. A record that cannot be read stops the restore there, since its scope is unknown; the next `hydrate()` tries again. Disposing the client keeps the stored calls: they are sent at the next start.

After a restart, the widget that made a call is gone:

- a success runs only the registration's `invalidates` and `invalidatesTags`. Optimistic cache writes are not persisted, so the restored cache only holds server data, and invalidating reconciles it;
- a failure shows in `entries` as `blocked` or `failed`, for the app to decide on, and in `mutationEvents`. `lastError` is then the error's `toString()`.

Delivery is **at-least-once**. If the app dies after the server applied a write but before the response arrived, the call is sent again on the next start, under the same `mutationId`. Send `meta.mutationId` as an idempotency key, or use client-generated IDs with create-as-upsert, so the server applies it once.

Do not put file bytes in the variables: key-value adapters such as `SharedPreferences` are not meant for binary payloads. Write the file to durable storage first and queue its path.

`clearStorage()` and `clear()` empty the queue, in memory and in storage. On logout, call `clear()`: it empties the queue before the cache, so the rollbacks of the discarded calls do not write the previous user's data back. A rollback written after an `await` in `onError` runs too late for that: restore the cache before any `await`. A `hydrate()` called during a `clearStorage()` waits for it. `clearCache()` does not touch the queue.
