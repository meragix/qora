## Fonctionnement du cache

Chaque résultat de requête est stocké en tant que `CacheEntry<T>` dans un `QueryCache` en mémoire, indexé par la clé de requête normalisée. Le cache pilote :

- **Réponses instantanées** : les données fraîches sont retournées sans appel réseau
- **SWR** : les données périmées sont retournées immédiatement pendant que les données fraîches sont récupérées en arrière-plan
- **Mises à jour réactives** : chaque `CacheEntry` contient un broadcast stream ; tout changement d'état atteint immédiatement tous les abonnés actifs

```text
fetchQuery(['users', 1])
  │
  ├─ Cache HIT  (frais)   → retourner les données immédiatement
  ├─ Cache HIT  (périmé)  → retourner les données périmées + revalider en arrière-plan
  └─ Cache MISS           → fetch → stocker → retourner les données
```

---

## Cycle de vie d'une entrée de cache

Une `CacheEntry<T>` traverse les étapes suivantes :

```text
Créée (Initial)
  │  fetchQuery / watchQuery déclenché
  ▼
Loading → Success / Failure
  │  staleTime écoulé
  ▼
Périmée (toujours en cache, accessible comme previousData)
  │  dernier abonné se désabonne
  ▼
Timer GC démarré (= gcTime)
  │  timer déclenché, aucun abonné actif
  ▼
Évincée (supprimée du cache)
```

Un sweep d'éviction en arrière-plan s'exécute également toutes les minutes pour supprimer les entrées inactives expirées.

## `staleTime` vs `gcTime`

Ces deux durées contrôlent des comportements indépendants :

| Propriété   | Défaut     | Contrôle                                               |
| ----------- | ---------- | ------------------------------------------------------ |
| `staleTime` | 0 (zéro)   | Quand déclencher une revalidation en arrière-plan      |
| `gcTime` | 5 minutes  | Quand supprimer une entrée inutilisée du cache         |

```dart [main.dart]
QoraOptions(
  staleTime: Duration(minutes: 5),   // données fraîches pendant 5 minutes
  gcTime: Duration(minutes: 10),  // données inutilisées conservées 10 min en cache
)
```

:::tip
`staleTime: Duration.zero` (la valeur par défaut) signifie que les données sont **toujours** considérées comme périmées. Qora sert quand même les données en cache immédiatement ; il revalide également en arrière-plan à chaque accès.
:::

## `staleTime` en détail

`staleTime` définit la fenêtre de fraîcheur. Pendant cette fenêtre, les données sont retournées depuis le cache sans aucune activité réseau :

```dart [main.dart]
// staleTime : 5 minutes

// t = 0:00 → fetch déclenché, Success stocké
// t = 0:01 → fetchQuery → Cache HIT (frais) : pas d'appel réseau
// t = 5:01 → fetchQuery → Cache HIT (périmé) : retourne les données en cache + revalide
// t = 5:01 → requête réseau déclenchée en arrière-plan
// t = 5:02 → Success mis à jour, abonnés au stream notifiés
```

Définir un `staleTime` long pour les données qui changent rarement :

```dart [main.dart]
// Données de configuration : valides pendant 1 heure
options: QoraOptions(staleTime: Duration(hours: 1)),

// Profil utilisateur : valide pendant 10 minutes
options: QoraOptions(staleTime: Duration(minutes: 10)),

// Prix en direct : toujours périmé (défaut)
options: QoraOptions(staleTime: Duration.zero),
```

---

## `gcTime` en détail

`gcTime` détermine combien de temps les données inactives restent en cache après le départ de tous les abonnés. Il préserve les données pour une re-navigation rapide :

```dart [main.dart]
// L'utilisateur quitte → dernier abonné annule → timer GC démarre
// L'utilisateur revient dans gcTime → entrée toujours en cache → affichage instantané
// L'utilisateur revient après gcTime → entrée évincée → fetch complet requis
```

```dart [main.dart]
// Liste de posts : conserver en cache 2 minutes après avoir quitté la page
options: QoraOptions(gcTime: Duration(minutes: 2)),
```

:::warning
`gcTime: Duration.zero` supprime l'entrée dès que tous les abonnés partent. La visite suivante repart toujours de `Initial`. Ce comportement est correct pour les données sensibles qui ne doivent pas survivre à la session courante.
:::

## Partage structurel (Structural Sharing)

Le partage structurel préserve l'égalité référentielle pour les données imbriquées inchangées entre les fetches. Quand un fetch retourne des données profondément égales aux données en cache, Qora conserve la référence précédente au lieu de la remplacer.

Cette fonctionnalité est activée par défaut (`QoraOptions.structuralSharing: true`). Elle répond directement au problème des reconstructions inutiles de widgets dans les interfaces utilisateur profondément imbriquées :

```dart [main.dart]
// Sans partage structurel : chaque fetch crée une nouvelle référence,
// ce qui oblige tous les widgets consommant cette requête à se reconstruire.
//
// Avec partage structurel (défaut) : si les données retournées sont
// structurellement identiques aux données en cache, l'ancienne référence
// est conservée. Les widgets qui vérifient identical(oldData, newData)
// ou == ignorent le rendu.

final client = QoraClient();
await client.fetchQuery<Map<String, dynamic>>(
  key: ['config'],
  fetcher: () => api.getConfig(),
  options: QoraOptions(structuralSharing: true),
);
```

### Fonctionnement

La comparaison d'égalité profonde est récursive :

- **Map** : compare la présence des clés et les valeurs récursivement
- **List** : compare le nombre d'éléments et les éléments récursivement
- **Set** : compare l'appartenance
- **Autres types** : utilise `==` (surcharger `==` et `hashCode` sur les classes de modèle personnalisées pour de meilleurs résultats)

```dart [main.dart]
final oldData = {'user': {'name': 'Alice', 'roles': ['admin']}};
final newData = {'user': {'name': 'Alice', 'roles': ['admin']}};

// structuralShare retourne oldData, elles sont profondément égales.
// Tout widget détenant oldData verra identical(oldData, newData) == true.
```

### Quand désactiver

Désactiver le partage structurel uniquement si la vérification d'égalité profonde devient un goulot d'étranglement mesuré avec de très grandes structures de données :

```dart [main.dart]
QoraOptions(structuralSharing: false),
```

### Portée

Le partage structurel s'applique à tous les chemins d'écriture du cache :

- `fetchQuery` après une réponse réseau réussie
- `setQueryData` pour les écritures manuelles dans le cache
- `setInfiniteQueryData` et `updateInfiniteQueryState` pour les requêtes infinies
- `hydrateQuery` lors de la restauration de données persistées dans une entrée non-initiale

## Éviction LRU

Quand `maxCacheSize` est défini sur `QoraClientConfig`, le cache applique une limite via une stratégie LRU (Least Recently Used) :

- L'entrée **accédée le moins récemment** et **sans abonnés actifs** est évincée pour faire de la place
- Les entrées actives (avec abonnés) ne sont **jamais évincées de force**

```dart [main.dart]
final client = QoraClient(
  config: QoraClientConfig(maxCacheSize: 100),
);
```

Chaque appel à `fetchQuery`, `watchQuery` ou `getQueryData` met à jour `lastAccessedAt`, maintenant les entrées en vie dans le classement LRU.

## Contrôle manuel du cache

### Lire le cache

```dart [main.dart]
// Obtenir uniquement les données (null si pas Success / pas de previousData)
final user = client.getQueryData<User>(['users', userId]);

// Obtenir l'état complet
final state = client.getQueryState<User>(['users', userId]);

// Inspecter toutes les clés en cache
for (final key in client.cachedKeys) {
  print(key);
}
```

### Écrire dans le cache

```dart [main.dart]
// Injecter des données directement : tous les streams watchQuery actifs sont notifiés
client.setQueryData<User>(['users', userId], updatedUser);

// Rollback vers un snapshot précédent
final snapshot = client.getQueryData<User>(['users', userId]);
client.setQueryData(['users', userId], optimisticUser);

try {
  await api.updateUser(userId, payload);
} catch (_) {
  client.restoreQueryData(['users', userId], snapshot);
}
```

### Invalider (marquer comme périmé)

```dart [main.dart]
// Clé unique : les streams actifs passent immédiatement à Loading
client.invalidate(['users', userId]);

// Plusieurs clés via prédicat
client.invalidateWhere((key) => key.firstOrNull == 'users');

// Basée sur des tags : revalider toutes les requêtes fournissant le tag 'post'
client.invalidateTags([QueryTag('post')]);

// Ressource spécifique : revalider uniquement les requêtes avec QueryTag('post', '123')
client.invalidateTags([QueryTag('post', '123')]);
```

L'invalidation basée sur les tags est l'approche la plus flexible. Les requêtes déclarent des tags via `providesTags` dans `QoraOptions`. Les mutations déclarent des tags via `invalidatesTags` dans `MutationOptions`. Les tags découplent l'invalidation de la structure des clés de requête : vous pouvez invalider des requêtes avec différents motifs de clés en un seul tag.

```dart [main.dart]
options: QoraOptions(
  providesTags: [QueryTag('post'), QueryTag('user', userId)],
)
```

Voir [MutationOptions.invalidatesTags](../05.api-reference/6.qora-mutation.md#invalidatestags) et [QoraOptions.providesTags](../05.api-reference/4.qora-options.md#providestags).

### Supprimer et vider

```dart [main.dart]
// Supprimer une entrée unique (GC immédiat)
client.removeQuery(['users', userId]);

// Vider le cache entier (ex. lors d'une déconnexion)
client.clear();
```

## Callback `onCacheEvict`

Réagir aux évictions de cache pour le logging ou la synchronisation du stockage :

```dart [main.dart]
final client = QoraClient(
  config: QoraClientConfig(
    onCacheEvict: (key) {
      analytics.track('cache_evict', {'key': key.toString()});
    },
  ),
);
```

## Configuration globale vs par requête

`gcTime` et `staleTime` peuvent être définis globalement via `QoraClientConfig.defaultOptions` et surchargés par requête :

```dart [main.dart]
final client = QoraClient(
  config: QoraClientConfig(
    defaultOptions: QoraOptions(
      staleTime: Duration(minutes: 5),  // défaut global
      gcTime: Duration(minutes: 10),
    ),
  ),
);

// Cette requête surcharge uniquement staleTime
await client.fetchQuery<Config>(
  key: ['config'],
  fetcher: api.getConfig,
  options: QoraOptions(staleTime: Duration(hours: 1)),
  // gcTime hérite toujours des 10 minutes du global
);
```
