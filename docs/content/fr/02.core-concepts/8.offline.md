La plupart des bibliothèques traitent « hors-ligne » comme une erreur de plus. Qora le traite comme un état : les lectures se **mettent en pause** au lieu d'échouer, les écritures peuvent être **mises en file**, et les deux reprennent seules au retour du réseau. Cette page décrit le modèle ; la [recette Network-Aware](../recipes/network-aware.md) détaille la configuration.

## Comment Qora sait que l'appareil est hors-ligne

Le client écoute un `ConnectivityManager`. `QoraScope.auto` attache `FlutterConnectivityManager`, basé sur `connectivity_plus` : une configuration Flutter standard n'a besoin de rien d'autre.

Deux conséquences à connaître :

- **Sans connectivity manager, le client se considère en ligne.** Rien ne se met en pause, et rien n'est rejoué à la reconnexion. Une application Dart pure peut attacher le sien avec `client.attachConnectivityManager(...)`.
- **La connectivité désigne une interface réseau, pas un serveur joignable.** Derrière un portail captif ou avec l'API en panne, l'appareil compte comme en ligne : les requêtes partent, sont retentées, et finissent en `Failure`.

## Deux axes : ce que vous avez, et ce qui se passe

Une requête a un état et un statut de fetch, et la gestion du hors-ligne vit dans le second :

- `QoraState` est **ce que vous avez** : `Initial`, `Loading`, `Success`, `Failure`, chacun portant la donnée quand il y en a une.
- `FetchStatus` est **ce que fait le moteur** : `fetching`, `paused` (en attente du réseau) ou `idle`.

`QoraBuilder` passe les deux à votre builder. Les combinaisons hors-ligne courantes :

| État | `fetchStatus` | Signification |
| ---- | ------------- | ------------- |
| `Loading`, `previousData` renseigné | `paused` | Hors-ligne, donnée en cache disponible, refetch en attente |
| `Loading`, sans `previousData` | `paused` | Hors-ligne et rien en cache : afficher un écran hors-ligne, pas un spinner |
| `Success` | `paused` | Hors-ligne en mode `offlineFirst` : donnée en cache servie, refetch en attente |
| `Success` | `idle` | Donnée fraîche, rien à faire |

Un fetch lancé hors-ligne ne lève pas d'exception dans les widgets. Appelé de façon impérative, `fetchQuery` renvoie la donnée en cache s'il y en a une, et lève sinon `QoraOfflineException`.

## Lectures : `NetworkMode`

`networkMode` décide de ce que fait une requête quand elle doit charger alors que l'appareil est hors-ligne. Réglez-le par requête dans `QoraOptions`, ou pour toutes les requêtes dans `defaultOptions`.

| Mode | Hors-ligne | À la reconnexion |
| ---- | ---------- | ---------------- |
| `online` (défaut) | Le fetch n'est pas envoyé. L'état devient `Loading(previousData: cache)`, le statut `paused` | Le fetch s'exécute |
| `offlineFirst` | Avec une donnée en cache : l'état reste `Success`, statut `paused`. Sans : comme `online` | Le fetch s'exécute |
| `always` | Le fetch est envoyé quand même, puis retenté et en échec comme toute erreur | Rien de particulier |

Utilisez `always` pour les fetchers qui n'ont pas besoin du réseau, comme une base locale. Utilisez `offlineFirst` quand un écran ne doit jamais repasser en chargement simplement parce que l'appareil a perdu le réseau.

## Écritures : la file de mutations hors-ligne

Une mutation ne se met pas en pause. Sans activation explicite, une mutation appelée hors-ligne envoie sa requête et échoue. Avec `offlineQueue: true` dans ses `MutationOptions`, elle est mise en file à la place :

```text
mutate(variables) hors-ligne
  1. onMutate s'exécute tout de suite → les mises à jour optimistes marchent hors-ligne
  2. l'appel est ajouté à la file
  3. état : MutationSuccess(isOptimistic: true) si optimisticResponse est défini,
            MutationPending sinon

reconnexion
  4. l'appel est envoyé, une fois, dans l'ordre de mise en file
     succès → onSuccess, invalidates, onSettled
     échec  → onError(error, variables, contexte de l'étape 1), onSettled
```

Trois propriétés comptent en pratique :

- **La file appartient au client, pas au widget.** Une écriture en file est envoyée même si l'écran qui l'a créée a été fermé.
- **Un rejeu en échec n'est pas retenté.** `onError` s'exécute avec le snapshot de `onMutate` : le rollback écrit pour le cas en ligne couvre donc aussi celui-ci. Prévenez l'utilisateur à cet endroit.
- **L'ordre est conservé, les dépendances ne sont pas vérifiées.** Si une création en file est rejetée, une mise à jour en file du même élément est quand même envoyée, et échoue à son tour. La [file des mutations enregistrées](#la-file-des-mutations-enregistrées) gère à la fois les nouvelles tentatives et les dépendances.

`optimisticResponse` ne définit que l'état propre de la mutation, par exemple pour afficher un badge « en file ». Les modifications des données en cache se font dans `onMutate`.

:::note
`QoraMutationBuilder` et `useMutation` utilisent tous deux la file (`useMutation` depuis `qora_hooks` 1.3.1). Un `MutationController` utilisé seul doit recevoir `isOnline` et `offlineQueue` explicitement.
:::

## La file des mutations enregistrées

Une [mutation enregistrée](./mutations.md#mutations-enregistrées) appelée avec `offlineQueue: true` passe par une seconde file, `client.mutationQueue`, conçue pour les écritures qui doivent finir par atteindre le serveur. Elle diffère de la file précédente sur trois points :

- **Chaque appel y passe, en ligne ou non.** Un appel fait en ligne est mis en file et envoyé aussitôt. Ainsi, une mise à jour faite en ligne ne peut pas doubler une création encore en attente depuis le mode hors-ligne. Un appel avec `networkMode: NetworkMode.always` ne passe pas par la file.
- **Les échecs transitoires sont retentés.** Un timeout ou une 503 ne perd pas l'écriture.
- **Les écritures dépendantes sont retenues.** Quand une écriture est rejetée, celles qui en dépendent ne sont pas envoyées.

```dart [main.dart]
final client = QoraClient()
  ..registerMutation<Todo, TodoInput>(
    'todos.save',
    mutator: (input, meta) => api.saveTodo(
      input,
      idempotencyKey: meta.mutationId,
    ),
    variables: todoInputSerializer,
    scope: (input) => 'todo:${input.id}',
    isPermanent: (error) => error is ApiException && error.statusCode < 500,
  );
```

```dart [todo_editor.dart]
MutationOptions<Todo, TodoInput, void>(
  mutationKey: 'todos.save',
  offlineQueue: true,
)
```

### Scopes

Les appels qui partagent un même `scope` forment une voie : ils sont envoyés un par un, dans l'ordre où ils ont été faits. Les appels sans scope partagent une voie globale. Les voies ne s'attendent pas entre elles, et envoient en parallèle jusqu'à `ReconnectStrategy.maxConcurrent` requêtes.

Un scope signifie « ces écritures dépendent les unes des autres ». Choisissez le plus étroit qui couvre les dépendances, en général l'ID de l'enregistrement, ou celui du parent pour les enfants : une tâche créée dans un projet lui-même créé hors-ligne doit utiliser le scope du projet, sinon elle peut partir avant que le projet existe. Un scope plus large que nécessaire retient plus d'écritures que besoin quand quelque chose échoue.

### Échecs

Qora ne voit pas les codes HTTP : c'est l'app qui classe les erreurs avec `isPermanent`, sur l'enregistrement ou pour toutes les clés dans `MutationQueueConfig` :

- **Transitoire** (par défaut, quand aucun prédicat ne dit le contraire) : l'appel reste en tête de sa voie et est retenté avec un backoff exponentiel tant que l'appareil est en ligne. Les délais doublent de 1 s jusqu'à 30 s, et chacun est tiré entre la moitié et la totalité de cette valeur : 0,5 à 1 s, puis 1 à 2 s, 2 à 4 s, 4 à 8 s. Perdre le réseau pendant une requête ne compte pas comme une tentative ; l'appel est renvoyé à la reconnexion. Après `maxAttempts` (5) tentatives, l'appel est traité comme permanent.
- **Permanent** : l'appel n'est pas retenté. Dans un scope, il devient `blocked`, et les appels qui le suivent dans ce scope sont `held` : sinon, une mise à jour envoyée après une création rejetée pourrait créer l'enregistrement avec des données qui n'ont jamais passé la validation. Sans scope, il devient `failed`, et la voie globale continue.

Sans aucun `isPermanent`, une erreur de validation est retentée pendant 7,5 à 15 secondes de backoff, plus la durée des cinq requêtes, avant de devenir `blocked` ou `failed`. Définissez-le pour arrêter plus tôt.

### Lire la file

`client.mutationQueue.entries` liste les appels en file, dans l'ordre. Chaque `QueuedMutation` porte sa `key`, son `scope`, ses `variables`, son `mutationId`, ses `attempts`, sa `lastError` et son `status` :

| Statut | Signification |
| ------ | ------------- |
| `queued` | Attend son tour, le réseau ou sa prochaine tentative |
| `sending` | Requête en cours |
| `blocked` | Attend une décision : échec définitif en tête de son scope, ou un appel qui le précédait dans le scope a été abandonné |
| `held` | Derrière un appel `blocked` du même scope ; non envoyé |
| `failed` | Échec définitif sans scope ; sorti de l'ordre de rejeu |

Un appel quitte la file quand il réussit ou quand l'app l'abandonne. Il y apparaît une fois en file pour de bon : après l'exécution de son `onMutate` et, avec `PersistQoraClient`, une fois stocké.

`entriesStream` émet les nouvelles entrées à chaque changement : un appel mis en file, envoyé, retenté, en échec, abandonné ou terminé. Les changements faits pendant une même exécution synchrone sont signalés une seule fois. Dans Flutter, [`MutationQueueBuilder`](../flutter-integration/network-status.md#mutationqueuebuilder) lit `entries`, écoute, et reconstruit à chaque changement :

```dart [sync_badge.dart]
MutationQueueBuilder(
  builder: (context, entries, child) => entries.isEmpty
      ? const SizedBox.shrink()
      : Text('${entries.length} change(s) to sync'),
)
```

Sans le widget, lisez d'abord `entries`, puis écoutez `entriesStream`.

Avec `qora_hooks`, [`useMutationQueue()`](../flutter-integration/hooks.md#usemutationqueue) renvoie la même liste et reconstruit le widget à chaque changement.

Un appel qui n'a plus d'appelant, parce qu'il a été restauré après un redémarrage ou retenté après que son point d'appel a été soldé, publie dans `client.mutationEvents` sous l'id `queue:<mutationId>` : `pending` quand il est envoyé pour la première fois, puis `success` ou `error`. Ses `metadata` portent `mutationKey` et `mutationId`.

### Décider pour un appel bloqué ou en échec

```dart [sync_screen.dart]
final queue = client.mutationQueue;

// Renvoyer tel quel, sous le même mutationId.
queue.retry(entry.mutationId);

// Le remplacer par des variables corrigées, sous un nouveau mutationId.
queue.retry(entry.mutationId, variables: fixedInput);

// L'abandonner. Les appels qu'il retenait deviennent bloqués à leur tour.
queue.discard(entry.mutationId);

// Abandonner toute la chaîne.
queue.discardScope('todo:42');
```

- **`retry(id)`** renvoie le même contenu sous le même `mutationId`, donc la déduplication côté serveur s'applique toujours. Utilisez-le quand un appel a épuisé ses tentatives sur des erreurs transitoires : le serveur l'a peut-être déjà appliqué.
- **`retry(id, variables: ...)`** remplace l'appel sur place, sous un nouveau `mutationId`. Pour modifier un enregistrement dont l'écriture est bloquée, retentez cette écriture avec de nouvelles variables au lieu de rappeler `mutate` : un nouvel appel serait retenu derrière celui qui est bloqué, et la file contiendrait deux versions de l'enregistrement.
- **`discard(id)`** retire l'appel. Les appels qui le suivent dans son scope visent peut-être un enregistrement qui n'existera jamais : ils deviennent `blocked`, et l'utilisateur décide pour chacun. Un appel abandonné pendant sa requête quitte `entries` aussitôt et n'est pas retenté ; si cette requête réussit malgré tout, les invalidations de l'enregistrement s'exécutent, et les appels qui le suivent restent `blocked`.
- **`clear()`** vide la file. Appelez-le à la déconnexion : une écriture en file appartient à l'utilisateur qui l'a faite. Videz la file avant le cache (`client.mutationQueue.clear()`, puis `client.clear()`) : les rollbacks `onError` qu'il déclenche écrivent dans le cache. `PersistQoraClient.clear()` fait les deux, dans cet ordre.

`discard`, `discardScope` et `clear` soldent chaque appel retiré fait pendant la session comme un échec : son `onError` reçoit une `MutationDiscardedException` avec le contexte d'`onMutate`, donc le rollback écrit pour une écriture rejetée annule aussi une écriture abandonnée.

### Ce que voit le point d'appel

Les callbacks du point d'appel s'exécutent pour les appels faits pendant la session, même après le démontage de son widget : un rollback dans `onError` atteint donc toujours le cache. Ils s'exécutent une fois par appel : quand il réussit, ou quand il échoue définitivement. Un `retry` ultérieur de cet appel n'exécute que les invalidations de l'enregistrement, car l'instantané d'`onMutate` est alors périmé, et le contrôleur qui a fait l'appel reste en `MutationFailure` même si le retry réussit. Une erreur levée par ces callbacks part dans la `Zone` courante au lieu de remonter à l'appelant de `mutate`.

`mutate` se résout quand l'appel réussit, échoue définitivement ou commence à attendre (hors-ligne, derrière un scope retenu, derrière ou en tête d'une voie qui attend une nouvelle tentative). Dans ce dernier cas, il se résout avec `null`, ou avec le résultat d'`optimisticResponse` si l'appareil était hors-ligne au moment de l'appel, et l'état de la mutation reste `MutationPending` (ou ce `MutationSuccess` optimiste) jusqu'à ce que l'appel aboutisse.

Pour ces appels, la politique de la file remplace `retryCount`, `retryDelay` et `retryCondition` du point d'appel.

Disposer le client résout chaque `mutate` en attente avec `null` sans exécuter de callback : l'app s'arrête, et le cache avec elle. Avec `PersistQoraClient`, les appels stockés sont conservés et envoyés au démarrage suivant.

Avec `PersistQoraClient`, la file survit à un redémarrage : voir [Persister la file](#persister-la-file).

## Reconnexion

Quand le connectivity manager signale le retour du réseau, le client :

1. **Rejoue les requêtes en pause** par lots. `ReconnectStrategy` fixe la taille des lots et un délai aléatoire entre eux (par défaut : 5 à la fois, jusqu'à 100 ms), pour qu'une centaine de requêtes en pause n'atteignent pas le serveur en même temps.
2. **Rejoue ensuite la file de mutations** précédente, après les lectures, une mutation à la fois.

La file des mutations enregistrées n'attend pas les lectures : elle reprend dès le retour du réseau, voie par voie, et les appels qui attendaient un délai de nouvelle tentative partent tout de suite.

Indépendamment, `QoraScope.auto` relance aussi les requêtes périmées affichées à l'écran quand l'application revient au premier plan.

## Entre deux redémarrages

| Quoi | Survit à un redémarrage ? |
| ---- | ------------------------- |
| Données de requêtes en cache | Oui, avec `PersistQoraClient` et un `StorageAdapter`. Voir [Persistance](../recipes/persistence.md) |
| Mutations enregistrées dans la file | Oui, avec `PersistQoraClient`, dans le même `StorageAdapter` |
| Appels sans `mutationKey` | Non : `OfflineMutationQueue` vit en mémoire |

### Persister la file

Avec `PersistQoraClient`, chaque appel enregistré est écrit dans le stockage avant de compter comme en file : `mutate` se résout, et `optimisticResponse` s'affiche, seulement une fois l'écriture terminée. Si l'écriture échoue, l'appel échoue avec cette erreur et `onError` s'exécute. Une app ne doit jamais dire « enregistré » à son utilisateur pour une écriture qui n'existe qu'en mémoire. Les appels qui le suivent dans son scope deviennent `blocked`.

Chaque appel est une entrée à part, sous une clé qui commence par `qora:mutation:`, donc elle n'entre jamais en collision avec les clés de requêtes ni avec les clés de l'app dans une box Hive ou un `SharedPreferences` partagés. Ses variables passent une seule fois par le sérialiseur `variables` de l'enregistrement, et le mutator les reçoit décodées depuis ce qui a été stocké : chaque tentative envoie donc le même contenu, pendant la session comme après un redémarrage. Modifier l'objet des variables après l'appel à `mutate` ne change rien. L'entrée est mise à jour après chaque tentative échouée, et supprimée après un succès ou un abandon. Un `retry` est stocké avant d'être envoyé ; si cette écriture échoue, l'appel attend de nouveau une décision, avec l'erreur de stockage comme `lastError`.

Enregistrez chaque mutation avant `hydrate()` :

```dart [main.dart]
final client = PersistQoraClient(storage: storage)
  ..registerMutation<Todo, NewTodo>(
    'todos.create',
    mutator: (input, meta) =>
        api.createTodo(input, idempotencyKey: meta.mutationId),
    variables: QoraSerializer<NewTodo>(
      toJson: (v) => v.toJson(),
      fromJson: (json) => NewTodo.fromJson(json as Map<String, dynamic>),
    ),
    invalidates: [['todos']],
  );

await storage.init();
await client.hydrate(); // restaure le cache, puis la file
```

`hydrate()` restaure la file avant les appels faits avant lui qui ne sont pas encore envoyés, avec le `mutationId`, les tentatives et le statut de chaque appel, et commence à envoyer. Un appel fait avant `hydrate()` peut déjà être en cours : hydratez avant que l'app puisse muter. Un appel stocké dont la clé n'est pas enregistrée, ou dont le `fromJson` des variables échoue, reste dans le stockage mais n'est pas restauré ; les appels stockés suivants de son scope non plus, pour ne jamais être envoyés avant lui. Les appels faits pendant la session dans ce scope ne sont pas retenus : enregistrez chaque clé avant `hydrate()`. Un enregistrement illisible arrête la restauration à cet endroit, puisque son scope est inconnu ; le `hydrate()` suivant réessaie. Disposer le client conserve les appels stockés : ils sont envoyés au démarrage suivant.

Les appels stockés par une ancienne version de l'app sont restaurés par la nouvelle. Quand la forme des variables d'une mutation change, mettez une version dans le payload et migrez les anciens payloads dans `fromJson` :

```dart
final todoInputSerializer = QoraSerializer<NewTodo>(
  // Incrémentez `v` à chaque changement de la forme stockée.
  toJson: (v) => {'v': 2, ...v.toJson()},
  fromJson: (json) {
    final map = json as Map<String, dynamic>;
    return switch (map['v']) {
      2 => NewTodo.fromJson(map),
      // La version 1, stockée par les anciennes versions de l'app, nommait le champ `name`.
      _ => NewTodo(map['name'] as String),
    };
  },
);
```

Sans cela, un payload que `fromJson` rejette n'est jamais envoyé et retient le reste de son scope jusqu'à `clearStorage()`, et seul `QoraClientConfig(debugMode: true)` le signale. Un payload que `fromJson` accepte encore mais lit autrement part tel que la nouvelle version le comprend.

Après un redémarrage, le widget qui a fait l'appel n'existe plus :

- un succès n'exécute que les `invalidates` et `invalidatesTags` de l'enregistrement. Les écritures optimistes dans le cache ne sont pas persistées : le cache restauré ne contient que des données serveur, et l'invalidation le réconcilie ;
- un échec apparaît dans `entries` comme `blocked` ou `failed`, pour que l'app décide, et dans `mutationEvents`. `lastError` est alors le `toString()` de l'erreur.

La livraison est **au moins une fois**. Si l'app meurt après que le serveur a appliqué une écriture mais avant l'arrivée de la réponse, l'appel est renvoyé au démarrage suivant, sous le même `mutationId`. Envoyez `meta.mutationId` comme clé d'idempotence, ou utilisez des ID générés côté client avec une création en upsert, pour que le serveur ne l'applique qu'une fois.

Ne mettez pas d'octets de fichier dans les variables : les adaptateurs clé-valeur comme `SharedPreferences` ne sont pas faits pour des contenus binaires. Écrivez d'abord le fichier dans un stockage durable et mettez son chemin en file.

Les variables sont stockées en JSON. Pour qu'elles ne restent pas en clair sur le disque, chiffrez l'adaptateur : voir [Chiffrer les données stockées](../recipes/persistence.md#chiffrer-les-données-stockées).

`clearStorage()` et `clear()` vident la file, en mémoire et dans le stockage. À la déconnexion, appelez `clear()` : il vide la file avant le cache, pour que les rollbacks des appels abandonnés ne réécrivent pas les données de l'utilisateur précédent. Un rollback écrit après un `await` dans `onError` arrive trop tard pour cela : restaurez le cache avant tout `await`. Un `hydrate()` appelé pendant un `clearStorage()` attend sa fin. `clearCache()` ne touche pas la file.
