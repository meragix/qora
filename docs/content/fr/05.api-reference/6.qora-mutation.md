## `MutationController`

Le contrôleur de cycle de vie central pour une seule mutation.

| Paramètre de type | Rôle                                                           |
| ----------------- | -------------------------------------------------------------- |
| `TData`           | La valeur retournée par le mutator en cas de succès            |
| `TVariables`      | La valeur passée à `mutate()`                                  |
| `TContext`        | Le snapshot retourné par `onMutate` (utilisé pour le rollback) |

### Constructeur

```dart
MutationController({
  MutatorFunction<TData, TVariables>? mutator,
  MutationOptions<TData, TVariables, TContext>? options,
  MutationTracker? tracker,
  Map<String, Object?>? metadata,
  bool Function()? isOnline,
  OfflineMutationQueue? offlineQueue,
  MutationQueue? mutationQueue,
  Future<void> Function(Object key)? invalidateQuery,
  Future<void> Function(List<QueryTag> tags)? invalidateTags,
  MutationRegistry? registry,
})
```

Passez soit `mutator`, soit `options.mutationKey` avec `registry` (en général `client.mutationRegistry`), pas les deux. Le constructeur lève une `ArgumentError` quand les deux ou aucun sont fournis, et une `StateError` quand la clé n'est pas enregistrée ou l'a été avec d'autres types. `QoraMutationBuilder` et `useMutation` passent `tracker`, `isOnline`, `offlineQueue`, `mutationQueue`, les callbacks d'invalidation et `registry` pour vous.

Avec `mutationQueue`, un appel fait avec `options.mutationKey` et `options.offlineQueue` passe par la [`MutationQueue`](#mutationqueue), en ligne ou non. `mutate` se résout alors quand l'appel réussit, échoue définitivement ou commence à attendre ; dans ce dernier cas avec `null`, ou avec le résultat d'`optimisticResponse` si l'appareil était hors-ligne au moment de l'appel. Les callbacks du point d'appel s'exécutent une fois par appel, et `retryCount`, `retryDelay` et `retryCondition` ne s'appliquent pas. Un `networkMode` à `NetworkMode.always` ne passe pas par la file.

```dart [post_repository.dart]
final controller = MutationController<Post, String, List<Post>?>(
  mutator: (title) => api.createPost(title),
  options: MutationOptions(
    onMutate: (title) async => client.getQueryData(['posts']),
    onError: (err, _, prev) async => client.restoreQueryData(['posts'], prev),
    onSuccess: (_, __, ___) async => client.invalidate(['posts']),
  ),
  tracker: client,
  metadata: {'category': 'content', 'resource': 'post'},
);
```

### Propriétés

#### `id`

```dart
final String id
```

Identifiant unique pour cette instance de contrôleur. Format : `mutation_N` (incrémental monotone). Utilisé comme clé dans `QoraClient.activeMutations` et `MutationUpdate.mutatorId`.

#### `mutator`

```dart
late final MutatorFunction<TData, TVariables> mutator
```

La fonction async qui effectue l'écriture. Nommée `mutator` pour faire écho à `fetcher` dans `fetchQuery`.

Pour une mutation enregistrée, elle appelle le mutator enregistré avec un nouveau `mutationId`. `mutate()` ne passe pas par elle : il garde un seul `mutationId` pour toutes les tentatives et tous les rejeux d'un appel.

#### `options`

```dart
final MutationOptions<TData, TVariables, TContext>? options
```

Callbacks de cycle de vie et configuration de retry. Voir `MutationOptions` ci-dessous.

#### `tracker`

```dart
final MutationTracker? tracker
```

Tracker optionnel (typiquement `QoraClient`) qui reçoit les notifications de changement d'état pour l'observabilité DevTools. Quand `null`, le contrôleur opère en mode standalone.

#### `metadata`

```dart
final Map<String, Object?>? metadata
```

Paires clé-valeur arbitraires transmises telles quelles à chaque `MutationUpdate` émis par ce contrôleur. Utiliser pour l'étiquetage DevTools sans modifier le schéma central.

#### `state`

```dart
MutationState<TData, TVariables> get state
```

Le snapshot d'état synchrone actuel.

#### `stream`

```dart
Stream<MutationState<TData, TVariables>> get stream
```

Un stream par abonné qui émet **immédiatement** l'état actuel à l'écoute (capture synchrone), puis transmet toutes les transitions suivantes.

Supporte plusieurs abonnés concurrents. Chaque abonnement obtient son propre stream soutenu par le contrôleur broadcast partagé : aucun événement n'est perdu entre `listen()` et le premier microtask.

### Méthodes

#### `mutate`

```dart
Future<TData?> mutate(TVariables variables)
```

Exécute la mutation. Séquence d'états :

1. Appelle `onMutate(variables)` → le résultat devient `TContext`
2. → `MutationPending`
3. Appelle `mutator(variables)` (avec retry optionnel)
4. → `MutationSuccess` + `onSuccess` + `onSettled`, ou → `MutationFailure` + `onError` + `onSettled`

Retourne `TData` en cas de succès, `null` en cas d'échec. Les erreurs ne sont **jamais** re-levées à l'appelant : elles sont capturées dans l'état `MutationFailure`.

**Lève** `StateError` si le contrôleur a été disposé.

#### `reset`

```dart
void reset()
```

Transition vers `MutationIdle`. Supprime également ce contrôleur de `tracker.activeMutations`.

**Lève** `StateError` si le contrôleur a été disposé.

#### `dispose`

```dart
void dispose()
```

Libère toutes les ressources et ferme le stream interne. Supprime silencieusement le contrôleur du tracker (aucun événement émis). Doit être appelé quand le contrôleur n'est plus nécessaire.

Après `dispose`, tout appel à `mutate` ou `reset` lève `StateError`.

## `MutationOptions`

Callbacks de cycle de vie et configuration de retry par mutation.

### Constructeur

```dart
const MutationOptions({
  Future<TContext?> Function(TVariables variables)? onMutate,
  Future<void> Function(TData data, TVariables variables, TContext? context)? onSuccess,
  Future<void> Function(Object error, TVariables variables, TContext? context)? onError,
  Future<void> Function(TData? data, Object? error, TVariables variables, TContext? context)? onSettled,
  int retryCount = 0,
  Duration retryDelay = const Duration(seconds: 1),
  bool Function(Object error, int attemptIndex)? retryCondition,
  NetworkMode networkMode = NetworkMode.online,
  bool offlineQueue = false,
  TData Function(TVariables variables)? optimisticResponse,
  List<Object>? invalidates,
  List<QueryTag>? invalidatesTags,
  String? mutationKey,
})
```

### Propriétés

#### `onMutate`

```dart
Future<TContext?> Function(TVariables variables)? onMutate
```

Appelé avant le mutator. Retourne `TContext` : le snapshot optimiste passé à `onError`/`onSettled` pour le rollback. Si ce callback lève, le mutator **n'est pas appelé** et le contrôleur transite directement vers `MutationFailure`.

#### `onSuccess`

```dart
Future<void> Function(TData data, TVariables variables, TContext? context)? onSuccess
```

Appelé après un mutator réussi, avant `onSettled`.

#### `onError`

```dart
Future<void> Function(Object error, TVariables variables, TContext? context)? onError
```

Appelé après l'échec du mutator (après tous les retries), avant `onSettled`. Utiliser `context` (le snapshot de `onMutate`) pour effectuer un rollback via `client.restoreQueryData`.

#### `onSettled`

```dart
Future<void> Function(TData? data, Object? error, TVariables variables, TContext? context)? onSettled
```

Appelé après chaque résultat : succès ou échec. `data` est non-null en cas de succès ; `error` est non-null en cas d'échec.

#### `retryCount`

```dart
final int retryCount
```

Nombre de tentatives de retry après l'échec initial. Défaut : `0` (pas de retry). Chaque retry utilise un backoff exponentiel : `retryDelay * 2^tentative`.

Ignoré par une mutation enregistrée avec `offlineQueue: true` : la [`MutationQueueConfig`](#mutationqueueconfig) du client le remplace.

#### `retryDelay`

```dart
final Duration retryDelay
```

Délai de base pour le premier retry. Défaut : `Duration(seconds: 1)`. Les retries suivants doublent : `1s, 2s, 4s, ...`

Ignoré par une mutation enregistrée avec `offlineQueue: true` : la [`MutationQueueConfig`](#mutationqueueconfig) du client le remplace.

#### `invalidates`

```dart
final List<Object>? invalidates
```

Liste des clés de requête à invalider automatiquement après une mutation réussie. Chaque clé est passée à `QoraClient.invalidate` après l'exécution de `onSuccess`, déclenchant un refetch des requêtes actives dont la clé correspond.

Remplace le pattern manuel courant :

```dart
// Avant : invalidation manuelle dans onSuccess
onSuccess: (data, vars, _) async { client.invalidate(['posts']); }

// Après : automatique via les options
invalidates: [['posts']],
```

Fonctionne également avec la relecture de la file hors-ligne, les requêtes sont invalidées lors de la relecture réussie, pas lors de l'émission optimiste initiale.

Nécessite un `QoraClient` ou un callback `invalidateQuery` câblé via `MutationController`. `QoraMutationBuilder` et `useMutation` fournissent cela automatiquement quand un ancêtre `QoraScope` est présent.

#### `invalidatesTags`

```dart
final List<QueryTag>? invalidatesTags
```

**Défaut :** `null`

Tags à invalider après une mutation réussie. Chaque requête qui fournit un tag correspondant est automatiquement re-récupérée. Fonctionne parallèlement à `invalidates` (qui cible directement les clés de requête) et est traité après lui.

La correspondance générique s'applique : invalider `QueryTag('post')` re-récupère TOUTES les requêtes qui fournissent un tag de type `'post'`, indépendamment de l'id.

```dart
// Re-récupère TOUTES les requêtes fournissant un tag 'post' (n'importe quel id).
MutationOptions(
  invalidatesTags: [QueryTag('post')],
)

// Re-récupère seulement les requêtes fournissant le tag spécifique 'post:123'.
MutationOptions(
  invalidatesTags: [QueryTag('post', '123')],
)
```

Nécessite un `QoraClient` ou un callback `invalidateTags` câblé via `MutationController`. `QoraMutationBuilder` et `useMutation` fournissent cela automatiquement quand un ancêtre `QoraScope` est présent.

#### `mutationKey`

```dart
final String? mutationKey
```

**Défaut :** `null`

Exécute la mutation enregistrée sous cette clé avec [`QoraClient.registerMutation`](./qora-client.md#registermutation) au lieu d'un mutator du point d'appel. Ne passez pas de `mutator` quand vous la définissez.

```dart
QoraMutationBuilder<Todo, NewTodo, void>(
  options: const MutationOptions(mutationKey: 'todos.create'),
  builder: (context, state, mutate) => const SizedBox(),
)
```

Les callbacks du point d'appel s'exécutent toujours pour les appels faits pendant la session, même après le démontage de son widget : un rollback dans `onError` atteint donc toujours le cache. Vérifiez `context.mounted` avant d'utiliser un `BuildContext` dans ces callbacks. Quand elle vaut `null`, le mutator du point d'appel s'exécute, comme avant. Voir [Mutations enregistrées](../core-concepts/mutations.md#mutations-enregistrées).

## `MutationState`

Hiérarchie de classes sealed représentant tous les états possibles d'une mutation.

```text
sealed MutationState
  ├── MutationIdle
  ├── MutationPending   { variables }
  ├── MutationSuccess   { data, variables }
  └── MutationFailure   { error, stackTrace?, variables }
```

### Getters communs

Disponibles sur toutes les variantes :

| Getter            | Type          | Description                                    |
| ----------------- | ------------- | ---------------------------------------------- |
| `isIdle`          | `bool`        | `true` dans `MutationIdle`                     |
| `isPending`       | `bool`        | `true` dans `MutationPending`                  |
| `isSuccess`       | `bool`        | `true` dans `MutationSuccess`                  |
| `isError`         | `bool`        | `true` dans `MutationFailure`                  |
| `dataOrNull`      | `TData?`      | Non-null uniquement dans `MutationSuccess`      |
| `errorOrNull`     | `Object?`     | Non-null uniquement dans `MutationFailure`      |
| `variablesOrNull` | `TVariables?` | `null` uniquement dans `MutationIdle`           |

### `when`

```dart
void when({
  void Function()? onIdle,
  void Function(TVariables variables)? onPending,
  void Function(TData data, TVariables variables)? onSuccess,
  void Function(Object error, StackTrace? stackTrace, TVariables variables)? onError,
})
```

Appelle un callback pour la variante correspondante. Les variantes non gérées sont ignorées silencieusement.

### `maybeWhen`

```dart
R maybeWhen<R>({
  required R Function() orElse,
  R Function()? onIdle,
  R Function(TVariables)? onPending,
  R Function(TData, TVariables)? onSuccess,
  R Function(Object, StackTrace?, TVariables)? onError,
})
```

Retourne la valeur du callback correspondant, ou `orElse()` si aucun ne correspond.

### `fold` (extension)

```dart
R fold<R>({
  required R Function() onIdle,
  required R Function(TVariables) onPending,
  required R Function(TData, TVariables) onSuccess,
  required R Function(Object, StackTrace?, TVariables) onError,
})
```

Mapper exhaustif : le compilateur impose que chaque variante soit gérée.

```dart [create_post_screen.dart]
final label = state.fold(
  onIdle: () => 'Créer',
  onPending: (_) => 'Création...',
  onSuccess: (post, _) => 'Créé : ${post.title}',
  onError: (err, _, __) => 'Erreur : $err',
);
```

### `status` (extension)

```dart
MutationStatus get status
```

Retourne la valeur d'enum `MutationStatus` à grain grossier : `idle | pending | success | error`.

enum MutationStatus { idle, pending, success, error }

Statut à grain grossier utilisé par `MutationUpdate` pour éviter les problèmes d'effacement de type générique au niveau du bus d'événements.

## `MutationUpdate`

Snapshot sans type d'une transition d'état de mutation. Émis par `QoraClient.mutationEvents` à chaque changement d'état de `MutationController`.

### Propriétés

| Propriété   | Type                       | Description                                                       |
| ----------- | -------------------------- | ----------------------------------------------------------------- |
| `mutatorId` | `String`                   | Identifiant unique du contrôleur (`mutation_N`)                   |
| `status`    | `MutationStatus`           | Statut à grain grossier au moment de l'émission                   |
| `data`      | `Object?`                  | Données de succès (type effacé). Non-null en cas de succès.       |
| `error`     | `Object?`                  | Erreur. Non-null en cas d'échec.                                  |
| `variables` | `Object?`                  | Variables passées à `mutate()`. `null` quand idle.                |
| `timestamp` | `DateTime`                 | Quand cet événement a été émis                                    |
| `metadata`  | `Map<String, Object?>?`    | Transmis depuis `MutationController.metadata`                     |

### Getters

| Getter       | Type   | Description                                                                             |
| ------------ | ------ | --------------------------------------------------------------------------------------- |
| `isIdle`     | `bool` | `status == MutationStatus.idle`                                                         |
| `isPending`  | `bool` | `status == MutationStatus.pending`                                                      |
| `isSuccess`  | `bool` | `status == MutationStatus.success`                                                      |
| `isError`    | `bool` | `status == MutationStatus.error`                                                        |
| `isFinished` | `bool` | `isSuccess \|\| isError` : utilisé par `QoraClient` pour purger automatiquement `activeMutations` |

## `MutationTracker`

Interface abstraite implémentée par `QoraClient`. Découple `MutationController` du client pour éviter les imports circulaires.

```dart
abstract interface class MutationTracker {
  void trackMutation<TData, TVariables>(
    String id,
    MutationState<TData, TVariables> state, {
    Map<String, Object?>? metadata,
  });

  void untrackMutation(String id);
}
```

Implémenter `MutationTracker` pour construire des DevTools personnalisés, un middleware de journalisation ou des espions de test :

```dart [mutation_logger.dart]
class MutationLogger implements MutationTracker {
  @override
  void trackMutation<TData, TVariables>(
    String id,
    MutationState<TData, TVariables> state, {
    Map<String, Object?>? metadata,
  }) {
    print('[$id] → ${state.runtimeType} ${metadata ?? ''}');
  }

  @override
  void untrackMutation(String id) => print('[$id] disposé');
}
```

## `QoraClient` : Observabilité des mutations

`QoraClient` implémente `MutationTracker` et expose deux surfaces pour observer les mutations suivies.

### `mutationEvents`

```dart
Stream<MutationUpdate> get mutationEvents
```

Stream broadcast en temps réel de chaque `MutationUpdate` de tous les contrôleurs suivis. Émet à chaque transition d'état : y compris `MutationIdle` (reset) et `MutationFailure`.

```dart [app_error_handler.dart]
client.mutationEvents.listen((event) {
  if (event.isError) {
    logger.error(
      '[${event.mutatorId}] Mutation échouée',
      event.error,
      event.metadata,
    );
  }
});
```

:::tip
`mutationEvents` est un stream broadcast : les événements émis avant votre abonnement sont perdus. Pour attraper les mutations démarrées avant l'abonnement, lire d'abord `activeMutations`.
:::

### `activeMutations`

```dart
Map<String, MutationUpdate> get activeMutations
```

Snapshot non modifiable de toutes les mutations **actuellement en cours** (pending), indexées par `MutationController.id`.

- Entrée **ajoutée** quand un contrôleur transite vers `MutationPending`
- Entrée **purgée automatiquement** quand la mutation se termine (`MutationSuccess` ou `MutationFailure`)
- Entrée **supprimée** quand le contrôleur revient à `MutationIdle` ou est disposé

```dart [devtools_panel.dart]
// Pattern de connexion tardive DevTools :
// 1. Lire le snapshot pour voir ce qui est actuellement en vol
final pending = client.activeMutations;

// 2. S'abonner au stream pour les mises à jour en temps réel (y compris les complétions)
client.mutationEvents.listen((event) {
  devtools.push(event);
});
```

`activeMutations` n'accumule jamais d'entrées "fantômes" pour les mutations terminées : c'est toujours un indicateur fiable de "en cours d'exécution".

### `debugInfo`

`QoraClient.debugInfo()` inclut l'état des mutations dans sa sortie :

```dart [main.dart]
print(client.debugInfo());
// {
//   total_queries: 5,
//   active_queries: 2,
//   inactive_queries: 3,
//   pending_requests: 0,
//   max_size: 100,
//   active_mutations: 1,   // ← mutations actuellement en attente
//   keys: [...]
// }
```

## `MutationMeta`

```dart
final class MutationMeta {
  final String mutationId;
  final int attempt;
}
```

Passée à un mutator enregistré à chaque tentative.

| Propriété    | Description                                                                                                                                  |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `mutationId` | UUID aléatoire version 4, généré à l'appel de `mutate()`. Identique pour toutes les tentatives de cet appel et pour son rejeu après reconnexion ; `MutationQueue.retry` avec de nouvelles variables en attribue un nouveau. |
| `attempt`    | Indice de tentative à partir de zéro : `0` pour le premier essai, `1` pour la première nouvelle tentative. Repart de `0` après `MutationQueue.retry`. |

Envoyez `mutationId` comme clé d'idempotence. La livraison est au moins une fois : une écriture dont la réponse s'est perdue est renvoyée avec le même `mutationId`, et seul le serveur peut ignorer le doublon.

## `MutationRegistry`

Les mutations qu'un client connaît par clé, accessibles via `client.mutationRegistry`. Enregistrez avec [`QoraClient.registerMutation`](./qora-client.md#registermutation) ; ne lisez le registre que pour vérifier ce qui est enregistré.

| Membre          | Description                                                                                                       |
| --------------- | ----------------------------------------------------------------------------------------------------------------- |
| `contains(key)` | Indique si une mutation est enregistrée sous `key`.                                                               |
| `keys`          | Les clés enregistrées, dans l'ordre d'enregistrement.                                                             |
| `register(...)` | Ajoute une `MutationRegistration`. Lève une `StateError` si la clé existe. Préférez `registerMutation`.           |
| `lookup(key)`   | Renvoie la `MutationRegistration` de `key`, ou `null`. Le type des variables doit correspondre exactement, et le type des données être celui enregistré ou un supertype ; sinon, lève une `StateError`. |

Une `MutationRegistration` contient ce que `registerMutation` a reçu : `key`, `mutator`, `variables`, `invalidates`, `invalidatesTags`, `scope` et `isPermanent`.

## `MutationQueue`

La file des mutations enregistrées, accessible par `client.mutationQueue`. Elle contient chaque appel fait avec `mutationKey` et `offlineQueue: true` jusqu'à ce qu'il réussisse ou que l'app l'abandonne. Avec `PersistQoraClient`, chaque appel est stocké avant de compter comme en file et survit à un redémarrage ; voir [Persister la file](../core-concepts/offline.md#persister-la-file). Voir [La file des mutations enregistrées](../core-concepts/offline.md#la-file-des-mutations-enregistrées) pour le modèle.

| Membre                             | Description |
| ---------------------------------- | ----------- |
| `entries`                          | `List<QueuedMutation>` : les appels en file, dans l'ordre où ils ont été faits. Un appel y apparaît une fois son `onMutate` exécuté et, avec `PersistQoraClient`, une fois stocké. |
| `entriesStream`                    | `Stream<List<QueuedMutation>>` : les nouvelles `entries` à chaque changement, une fois par exécution synchrone. Broadcast. |
| `length`, `isEmpty`                | Nombre d'appels en file, tous statuts confondus. |
| `retry(mutationId)`                | Renvoie tel quel un appel `blocked` ou `failed`, sous le même `mutationId`. |
| `retry(mutationId, variables: v)`  | Remplace un appel `blocked` ou `failed` par de nouvelles variables, sous un nouveau `mutationId`. Son scope ne change pas. |
| `discard(mutationId)`              | Retire un appel. Les appels qui le suivent dans son scope deviennent `blocked`. Un appel en cours quitte `entries` aussitôt et n'est pas retenté. |
| `discardScope(scope)`              | Retire tous les appels de `scope`. |
| `clear()`                          | Retire tous les appels. À utiliser à la déconnexion. |

Dans Flutter, [`MutationQueueBuilder`](../flutter-integration/network-status.md#mutationqueuebuilder) reconstruit avec `entries` à chaque changement ; avec `qora_hooks`, [`useMutationQueue()`](../flutter-integration/hooks.md#usemutationqueue) aussi.

`retry` lève une `StateError` pour un id inconnu ou un appel qui n'est ni `blocked` ni `failed`, et une `ArgumentError` quand `variables` ne correspondent pas au type enregistré. Le nombre de tentatives repart de zéro. Un appel `blocked` retenté reste en tête de son scope ; un appel `failed` retenté revient en tête de la voie globale.

`discard`, `discardScope` et `clear` soldent chaque appel retiré fait pendant la session comme un échec : l'`onError` du point d'appel reçoit une [`MutationDiscardedException`](#mutationdiscardedexception) avec son contexte d'`onMutate`.

## `QueuedMutation`

```dart
final class QueuedMutation {
  final String mutationId;
  final String key;
  final String? scope;
  final Object? variables;
  final DateTime enqueuedAt;
  final int attempts;
  final Object? lastError;
  final QueuedMutationStatus status;
}
```

Un instantané d'un appel en file. `attempts` compte les tentatives depuis la mise en file ou le dernier `retry` de l'app. `lastError` est l'erreur de la dernière tentative échouée ; pour un appel restauré par `PersistQoraClient.hydrate()`, c'est le `toString()` de cette erreur.

---

## `QueuedMutationStatus`

| Valeur    | Signification |
| --------- | ------------- |
| `queued`  | Attend son tour, le réseau ou sa prochaine tentative. |
| `sending` | Requête en cours. |
| `blocked` | Échec définitif en tête de son scope, ou un appel qui le précédait dans le scope a été abandonné ; attend `retry` ou `discard`. |
| `held`    | Derrière un appel `blocked` du même scope ; non envoyé. |
| `failed`  | Échec définitif sans scope ; hors de l'ordre de rejeu jusqu'à `retry` ou `discard`. |

## `MutationQueueConfig`

```dart
const MutationQueueConfig({
  int maxAttempts = 5,
  Duration initialDelay = const Duration(seconds: 1),
  Duration maxDelay = const Duration(seconds: 30),
  bool Function(Object error)? isPermanent,
})
```

Se configure par `QoraClientConfig.mutationQueue`.

| Paramètre      | Description |
| -------------- | ----------- |
| `maxAttempts`  | Tentatives, la première comprise, avant qu'un appel en échec transitoire soit traité comme permanent. |
| `initialDelay` | Délai avant la première nouvelle tentative. Il double à chaque tentative, jusqu'à `maxDelay`. La moitié de chaque délai est aléatoire. |
| `maxDelay`     | Borne supérieure du délai entre deux tentatives. |
| `isPermanent`  | Indique si une erreur rejette définitivement un appel, pour les enregistrements sans leur propre `isPermanent`. Quand `null`, toute erreur est transitoire. |

Un prédicat qui lève une exception compte comme permanent : une erreur impossible à classer n'est jamais retentée indéfiniment.

---

## `MutationDiscardedException`

```dart
final class MutationDiscardedException implements Exception {
  final String mutationId;
  final String key;
}
```

L'erreur passée à `onError`, et stockée dans `MutationFailure`, quand l'app retire un appel en file avec `MutationQueue.discard`, `discardScope` ou `clear`. `mutationId` et `key` identifient l'appel retiré.

---

## `MutatorFunction`

```dart
typedef MutatorFunction<TData, TVariables> =
    Future<TData> Function(TVariables variables);
```

Alias de type pour la fonction de mutation. Fait écho à `QueryFunction<T>` pour la cohérence avec la convention de nommage `fetcher`/`mutator` dans toute l'API.
