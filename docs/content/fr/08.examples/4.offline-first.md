## Objectif

La connexion mobile coupe sans arrêt : tunnels, ascenseurs, mode avion. Et une app peut être tuée pendant qu'elle est hors ligne. Cet exemple montre une app de todos qui reste utilisable dans les deux cas :

- la liste s'affiche depuis le cache, et depuis le stockage au démarrage à froid ;
- l'UI sait qu'elle est hors ligne, au lieu de tourner indéfiniment ;
- les todos créés, cochés ou supprimés hors ligne apparaissent tout de suite, **survivent à un redémarrage**, et sont envoyés dans l'ordre au retour du réseau ;
- une écriture refusée par le serveur est montrée à l'utilisateur, qui choisit de la renvoyer ou de l'abandonner.

Aucun code de synchronisation sur mesure : l'app enregistre ses écritures, et lit la file pour montrer ce qui est en attente.

:::tip
**Essayez sans toucher au Wi-Fi ni tuer l'app.** Le bouton antenne de la barre d'app passe l'appareil hors ligne, et la fausse API échoue tant qu'il l'est. Le bouton redémarrer dispose le client et en construit un nouveau depuis le stockage, comme un vrai redémarrage. Le bouton de synchronisation ouvre la file. Créez un todo dont le titre contient « reject » pour voir une écriture refusée par le serveur.
:::

## Fonctionnalités démontrées

- **`PersistQoraClient`** : les données chargées et les écritures en file vont dans un `StorageAdapter` ; `hydrate()` restaure les deux
- **Mutations enregistrées** : `todos.create`, `todos.toggle` et `todos.delete` sont déclarées une fois, avec un serializer pour leurs variables, pour qu'une écriture mise en file par une session puisse être envoyée par la suivante
- **`meta.mutationId`** : envoyé comme clé d'idempotence, pour qu'une écriture envoyée deux fois soit appliquée une fois
- **Scopes** : toutes les écritures d'un todo partagent le scope `todo:<id>`, pour qu'une coche ne passe jamais devant la création de son todo
- **`isPermanent`** : une 4xx n'est pas retentée ; l'écriture est `blocked` et celles derrière elle sont `held`
- **`MutationQueueBuilder`** : la liste superpose les écritures en attente tirées de `mutationQueue.entries`, et un panneau de synchronisation les liste avec renvoi et abandon
- **`NetworkMode.offlineFirst`**, **`FetchStatus.paused`**, **`NetworkStatusIndicator`** et **`ReconnectStrategy`** côté lecture

## Architecture

```text
main.dart
├── InMemoryStorageAdapter().init()   ← le « disque » : survit au redémarrage simulé
├── SimulatedNetwork()                ← le réseau de l'appareil, basculé depuis l'UI
├── TodoApi(network)                  ← le serveur, avec clés d'idempotence
└── OfflineTodoApp                    ← reconstruit le client au redémarrage
    └── startClient(storage, api)
        ├── PersistQoraClient(...)
        ├── registerAllSerializers()  ← données de requête écrites dans le stockage
        ├── registerTodoMutations()   ← écritures stockables et rejouables
        └── hydrate()                 ← liste en cache, puis écritures en file
```

Le démarrage suit l'ordre dont une vraie app a besoin : tout enregistrer, puis hydrater.

```dart [lib/main.dart]
Future<PersistQoraClient> startClient(
  StorageAdapter storage,
  TodoApi api,
) async {
  final client = PersistQoraClient(
    storage: storage,
    persistDuration: const Duration(days: 30),
    config: QoraClientConfig(
      defaultOptions: const QoraOptions(
        staleTime: Duration(minutes: 5),
        networkMode: NetworkMode.offlineFirst,
      ),
      // At most 3 concurrent requests on reconnect, 150 ms jitter.
      reconnectStrategy: const ReconnectStrategy(
        maxConcurrent: 3,
        jitter: Duration(milliseconds: 150),
      ),
      debugMode: kDebugMode,
    ),
  );
  registerAllSerializers(client);
  registerTodoMutations(client, api);
  await client.hydrate();
  return client;
}
```

Le redémarrage simulé démonte le `QoraScope`, qui dispose le client : comme un processus tué, il arrête d'envoyer et garde ce qu'il a stocké. Ce n'est qu'ensuite que le client suivant est construit et hydraté, pour que deux clients n'envoient jamais la même file.

Dans une vraie app, remplacez `InMemoryStorageAdapter` par un adapter adossé à un vrai stockage (voir la [recette Persistance](../recipes/persistence.md)), et `SimulatedConnectivityManager` par `FlutterConnectivityManager()`, ou utilisez `QoraScope.auto`.

## Détails d'implémentation

### Enregistrer les écritures

Une écriture qui peut être envoyée par une autre session ne peut pas vivre dans un widget : après un redémarrage, ce widget n'existe plus. Chaque écriture est enregistrée une fois, avec son mutator, un serializer pour ses variables, un scope et les erreurs définitives.

```dart [lib/features/todos/data/todo_mutations.dart]
void registerTodoMutations(QoraClient client, TodoApi api) {
  // Every write to one todo shares its scope: a toggle queued after an
  // offline create waits for it, and is held if the server rejects it.
  String scope(String id) => 'todo:$id';
  bool isPermanent(Object error) =>
      error is ApiException && error.isClientError;

  client
    ..registerMutation<Todo, CreateTodoInput>(
      'todos.create',
      mutator: (input, meta) async {
        // meta.mutationId stays the same across retries and restarts: the
        // server uses it to apply this write once.
        final todo = await api.createTodo(
          input,
          idempotencyKey: meta.mutationId,
        );
        _patchList(
          client,
          (list) => [...list.where((t) => t.id != todo.id), todo],
        );
        return todo;
      },
      variables: QoraSerializer<CreateTodoInput>(
        toJson: (v) => v.toJson(),
        fromJson: (json) =>
            CreateTodoInput.fromJson(json as Map<String, dynamic>),
      ),
      scope: (input) => scope(input.id),
      isPermanent: isPermanent,
      invalidates: [todosKey],
    );
  // todos.toggle and todos.delete follow the same pattern.
}
```

Deux choix font fonctionner les scopes :

- **L'id du todo est généré sur l'appareil**, dans `CreateTodoInput.newTodo`, et le serveur crée par upsert sur cet id. Un todo créé hors ligne a son id définitif tout de suite : une coche ou une suppression mise en file après lui le cible, et tombe dans le même scope. Avec des ids générés par le serveur, la coche aurait besoin d'un id qui n'existe pas encore.
- **Le mutator met à jour la liste en cache** avec la réponse du serveur. La file retire un appel dès qu'il réussit, et la liste montre les écritures en attente depuis la file (plus bas) : sans cette mise à jour, un nouveau todo disparaîtrait jusqu'à la fin du refetch déclenché par `invalidates`.

### Les appeler

Les points d'appel nomment la clé ; ils ne passent pas de mutator.

```dart [lib/features/todos/ui/todo_screen.dart]
QoraMutationBuilder<Todo, CreateTodoInput, void>(
  options: const MutationOptions(
    mutationKey: 'todos.create',
    offlineQueue: true,
  ),
  // Never disabled while a call is pending: offline, each new todo is
  // queued behind the others, and shows in the list at once.
  builder: (context, _, create) => FloatingActionButton.extended(
    onPressed: () async {
      final title = await _askTitle(context);
      if (title != null) await create(CreateTodoInput.newTodo(title));
    },
    icon: const Icon(Icons.add),
    label: const Text('Add Todo'),
  ),
)
```

Chaque appel passe par `client.mutationQueue`, en ligne ou non, et est écrit dans le stockage avant que `mutate` rende la main.

### Montrer les écritures en attente depuis la file

La liste est celle du serveur, avec les écritures en file superposées. L'état en attente est lu dans la file plutôt qu'écrit dans le cache par `onMutate` : la file est stockée et restaurée, les écritures optimistes dans le cache ne le sont pas. Un todo créé hors ligne reste donc affiché après un redémarrage, jusqu'à ce que le serveur le confirme.

```dart [lib/features/todos/ui/todo_screen.dart]
MutationQueueBuilder(
  builder: (context, entries, _) => _TodoList(
    todos: applyQueue(state.dataOrNull ?? const [], entries),
    isRefreshing: fetchStatus == FetchStatus.fetching,
    isOffline: fetchStatus == FetchStatus.paused,
  ),
)
```

`applyQueue` est une fonction pure : une création en file ajoute son todo, une coche le modifie, une suppression en route le masque. Chaque todo reçoit un état de synchronisation, tiré des statuts de ses écritures :

```dart [lib/features/todos/data/todo_view.dart]
for (final entry in queue) {
  switch (entry.variables) {
    case CreateTodoInput(:final id, :final title):
      todos[id] ??= Todo(id: id, title: title, completed: false);
      mark(id, entry.status);
    case ToggleTodoInput(:final id, :final completed):
      final todo = todos[id];
      if (todo != null) todos[id] = todo.copyWith(completed: completed);
      mark(id, entry.status);
    case DeleteTodoInput(:final id):
      mark(id, entry.status);
      // A delete on its way hides the todo; a refused one leaves it shown,
      // flagged, so the user can see what did not go through.
      if (sync[id] == SyncState.pending) todos.remove(id);
  }
}
```

### Le panneau de synchronisation

La barre d'app affiche le nombre d'écritures en attente, en rouge quand l'une d'elles attend l'utilisateur. Le panneau liste `entries` en direct, et propose une décision sur une écriture `blocked` ou `failed` :

```dart [lib/features/sync/sync_panel.dart]
trailing: _needsDecision(entry)
    ? Row(
        mainAxisSize: MainAxisSize.min,
        children: [
          // Same payload, same mutationId: the server still
          // deduplicates it.
          TextButton(
            onPressed: () => queue.retry(entry.mutationId),
            child: const Text('Retry'),
          ),
          // The writes it held become blocked in turn.
          TextButton(
            onPressed: () => queue.discard(entry.mutationId),
            child: const Text('Discard'),
          ),
        ],
      )
    : null,
```

### Scénarios à essayer

```text
Hors ligne, puis redémarrage
  1. Passer hors ligne, créer « Buy milk »  → stocké, affiché avec une icône d'attente
  2. Redémarrer                             → hydrate() le restaure : toujours affiché, toujours en attente
  3. Repasser en ligne                      → envoyé sous le même mutationId, confirmé

Tué en plein envoi
  1. En ligne, créer « Call mom », redémarrer aussitôt
  2. Le serveur a appliqué la première requête ; la nouvelle session la renvoie
  3. Même mutationId : le serveur renvoie le premier résultat, un seul todo

Refusé
  1. Hors ligne, créer « Please reject me », puis le cocher
  2. Repasser en ligne                      → création refusée (422) : blocked ; la coche est held
  3. Panneau de synchro → Discard           → la coche devient blocked : l'abandonner aussi
```

Les tests de widgets de l'exemple jouent ces trois scénarios.

### Hors ligne sans rien en cache

Quand l'appareil est hors ligne et que rien n'est en cache, le fetch se met en pause au lieu de partir : l'état est `Loading` sans données précédentes, et `fetchStatus` vaut `FetchStatus.paused`. Un spinner tournerait jusqu'au retour du réseau, donc ce cas a son propre écran :

```dart [lib/features/todos/ui/todo_screen.dart]
if (state.dataOrNull == null && fetchStatus == FetchStatus.paused) {
  return const _OfflineEmptyState();
}
```

## Limites à connaître

- **Cette démo utilise `InMemoryStorageAdapter`** : le stockage survit au redémarrage simulé, pas à un vrai. Avec un adapter sur disque, le même code restaure la liste et la file au démarrage à froid.
- **La livraison est at-least-once.** Le faux serveur déduplique sur la clé d'idempotence ; un vrai serveur doit faire de même, ou créer par upsert sur des ids générés par le client.
- **Les callbacks du point d'appel ne s'exécutent pas après un redémarrage.** Les `invalidates` de l'enregistrement, si : c'est pourquoi la liste se réconcilie depuis le serveur, et pourquoi le mutator met le cache à jour.
